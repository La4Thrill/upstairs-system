```

┌────────────────────┐    ┌───────────────────────────────┐   ┌────────────────────┐
│ SIM-01 上楼(判层)   │───►│ device 通道表 g_devices[16]    │   │ 设备列表 / 切换     │

┌────────────────────┐    │                               │   │ 原始数据回看（库）  │
│ STM32 真实终端      │───►│ POST /api/ingest（设备密钥）    │   │ 历史记录（按设备）  │
│ WiFi + LSM9DS0     │    │                               │   │ 角色登录             │
```

**分层：** 数据源（simulator / ingest）→ 设备通道（`Device`）→ 算法（`gait_algo`）→ 存储（`db_manager`）→ 展示（`web_server` + 前端）。

关键点：**模拟终端和真实终端写的是同一个 `Device` 结构**，所以硬件接进来时前端、数据库、算法都不用改。

## 3. 算法（为什么能从 465 步变成 68 级台阶）

### 3.1 旧版本为什么错

1. 数据是**有符号 16 位原始计数**（`65338` 实际是 `-198`），旧代码用 `%f` 直接读成 65338，符号和量纲全丢 → `|a|` 常年在 9 万左右。
2. 台阶阈值是常数 `1200`（搭配 `80` 的增量门限），对 9 万的基线恒为真，`cooldown=2` 只能挡住 2 个样本 → 平均每 5.35 个样本就"走一步"，层数实际等于"样本数 / 107"。
3. 采样间隔写 100 ms，与数据集 50 Hz 不符 → 时间轴、步频错 5 倍。

### 3.2 处理链（`gait_algo.c`）

```
原始 LSB(int16)
  │  ①符号还原 + 量纲换算：/16384 → g（LSM9DS0 ±2g）；/114.29 → °/s（±245dps）
  ▼
加速度模长 |a| (g)
  │  ②去重力：一阶低通 α=0.03（@50Hz ≈0.7s），dyn = |a| − 重力
  ▼
动态加速度 dyn ──③滑动平均（窗长按 fs 换算，@50Hz = 5 点 / 100 ms）
  │  ④台阶检测：迟滞 0.18g / 0.09g + 不应期 300 ms（按 fs 换算成样本数）
  ▼
台阶事件 ──►⑤台阶数 mod 11 → 平台（梯段）事件
        ──►  台阶数 mod 22 → 到达楼层事件
        ──►  台阶数 mod 15 → "每 15 级"提示（旧模板遗留，见 §11）
  │  ⑥动态能量 EMA：RMS<0.14g 持续 0.6s → 平台(真停顿)事件
  ▼
事件 → 提示音（音色区分）+ /api/status + SQLite
```

> **采样率无关（P0-5）**：`refractory`（300 ms）、`gravity_alpha`（0.03 @50Hz）、滑动平均窗（100 ms）
> 这三个量存的是**物理时间**，由 `gait_apply_fs()` 按 `cfg->fs` 换算成样本数/系数。
> `fs == 50` 时换算结果与旧硬编码版本逐位一致，所以数据集上的结论（68 级 / 3 层 / 82 级·分⁻¹）不变。
> 端侧定时器改成 40 Hz 或 100 Hz 也不用改算法，只要报文里的 `fs` 是对的。

### 3.3 参数标定依据

| 参数 | 取值 | 依据 |
|---|---|---|
| 采样率 fs | 50 Hz | `九轴数据文件/ReadMe.doc`：所有场景 50 Hz |
| 加速度灵敏度 | 16384 LSB/g | LSM9DS0 ±2g（0.061 mg/LSB） |
| 步态阈值 | 0.18 g（上楼）/ 0.10 g（平地行走） | 上楼动态幅度大；行走起伏小，同阈值会漏检（0.18g→57 级/分，0.10g→91 级/分） |
| 不应期 | 300 ms | 人正常步频上限约 3 步/s |
| 每半层台阶 | 11 级 | 68 级 ÷ 6 个梯段 ≈ 11.3 |
| 每层台阶数 | 22 级 | 68 级 ÷ 3 层 ≈ 22.7，与住宅 18~22 级/层吻合 |
| 楼层上限 | 99 层 | 课题要求 |

**阈值鲁棒性**（上三层楼数据，判层模式）：

| 步态阈值 (g) | 0.10 | 0.12 | 0.14 | 0.16 | 0.18 |
|---|---|---|---|---|---|
| 检出台阶 | 82 | 79 | 74 | 71 | 68 |
| 判出楼层 | **3** | **3** | **3** | **3** | **3** |

## 4. 设备与多终端

### 4.1 设备通道

`Device`（`global_vars.h`）一台设备一份：算法状态、波形缓冲、计数、在线状态、设备密钥、归属采集对象。
默认最多 16 台（`MAX_DEVICES`）。

### 4.2 默认模拟终端

| 终端 | 采集对象 | 默认场景 | 行为 |
|---|---|---|---|
| `SIM-01` | collector1 | `upstairs3` | 上楼，判层（0.18g） |
| `SIM-02` | collector2 | `dailywalk` | 日常行走，只计步（0.10g），验证"不误判楼层" |

两台终端各有独立线程、独立文件进度、独立计数——网页上能看到两台设备同时推进、数值互不影响。

场景可单独加载：`POST /api/sim/load` 带 `device_id`。

### 4.3 真实设备接入

见 `docs/hardware-protocol.md`。要点：

```http
POST /api/ingest
X-Device-Key: <首次上报时下发>
{"device_id":"STM32-01","fs":50,"samples":[[gx,gy,gz,ax,ay,az], ...]}
```

- 首次上报自动登记并下发密钥；
- 之后密钥不匹配返回 `403 invalid_device_key`；
- 响应里带 `events`（`half` / `floor` / `pause` / `steps15` / `top`），**提示音在端侧响**；
- 可带 `"user":"collector2"` 把设备绑定到采集对象。

## 7. 安全、会话与数据治理

### 7.1 口令：加盐 SHA-256

- `crypto_sha256.c` 自带 SHA-256（不依赖 OpenSSL），已用 FIPS 标准向量自测（见 `tools/selftest.c`）。
- 库里只存 `sha256$<32位盐>$<64位摘要>`，同一口令两次生成结果不同（盐随机）。
- **旧库自动迁移**：启动时把仍是明文的口令就地升级，日志会打印 `[DB] 4 个明文口令已升级为加盐哈希`。
- 局限：这是"快速哈希"，抗暴力破解能力有限；课程演示够用，生产环境应换 PBKDF2/Argon2。

### 7.2 会话：持久化到 SQLite

- 登录后 token 写入 `sessions` 表（含 `expires_at`，默认 12 小时）；
- 服务重启后同一 token 仍可继续用（实测：重启后 `/api/session` 仍返回 200）；
- `POST /api/logout` 立即删除该 token，之后访问返回 401；
- 过期 token 在启动时与后台维护线程里清理。

### 7.3 原始数据保留策略

| 项 | 默认值 | 说明 |
|---|---|---|
| 每台设备保留行数 | 20000（≈6.7 分钟 @50Hz） | 超出后删最旧的 |
| 保留天数 | 7 天 | 原始样本、进度快照、事件明细都按天清理 |
| 清理时机 | 启动时 + 每 60 s | `server.c` 的后台维护线程 |

管理员可临时手动触发（也用于演示/测试）：

```http
POST /api/maintenance/retention
{"keep": 5000, "days": 3}
→ {"status":"retention_done","raw_deleted":1300,"raw_rows_now":100,...}
```

## 8. 陀螺验证（先验，再谈方向判别）

课题给的数据集里三轴角速度**几乎是常量**：模长均值 10.26 °/s、标准差只有 0.061 °/s。
也就是说"陀螺没出数"，任何依赖陀螺的功能（上下楼方向判别、平台转弯检测）都不能做。

### 8.1 离线/实时验证工具

```powershell
gcc -std=c99 -O2 -o gyro_check.exe tools\gyro_check.c -lm
.\gyro_check.exe "D:\数据文件\数据文件\九轴数据文件\上三层楼数据.txt"
```

对数据集的输出：

```
角速度模长    : 均值 10.26 °/s, 标准差 0.061 °/s
  gyro_x       : 均值    -5.77 °/s, 标准差  0.073 °/s
  gyro_y       : 均值     1.49 °/s, 标准差  0.062 °/s
  gyro_z       : 均值    -8.35 °/s, 标准差  0.054 °/s
明显转动样本  : 0 个 (0.00%，相对基线偏离 > 5 °/s)
结论          : 【陀螺无效】近似常量偏置，数据里没有真实转动
```

判据：模长标准差 < 0.2 °/s → 无效；0.2~0.5 → 存疑；≥ 0.5 且有明显转动样本 → 有效
（用一份带 20 dps 正弦的合成数据验证过，会判"有效"）。

接上真机后可以边转板子边看：

```powershell
$port = New-Object System.IO.Ports.SerialPort COM3,115200
$port.Open()
while ($true) { $port.ReadLine() } | .\gyro_check.exe - --every 200
```

### 8.2 服务端也一直在算

每台设备都在维护角速度的在线均值/方差（Welford），`/api/status` 与 `/api/devices` 返回：

| 字段 | 含义 |
|---|---|
| `gyro_std` | 角速度模长标准差（°/s） |
| `gyro_valid` | 是否有效（样本 ≥ 200 且 σ ≥ 0.5 °/s） |
| `gyro_samples` | 参与统计的样本数 |

网页"爬楼结果"里会显示 `陀螺：无效（σ=0.06 °/s）` 并说明"当前只用加速度判层与计步"。
真机陀螺一旦有数据，这里会自动变成绿色"有效"，再做方向判别就有依据了。

### 10.4 多数据集回归（含负样本）—— 直接验收"会不会误判楼层"

只看"上三层楼能判出 3 层"是不够的：那只证明算法在这一份数据上对。
真正要回答的是"**换一份别的运动数据，会不会也判出楼层**"。

仓库里的 `testdata/` 放了老师给的其余 5 份数据（下楼 / 跑步 / 跳绳 / 仰卧起坐 / 混合），
`data1.txt`、`data2.txt` 就是上三层楼和日常行走，合起来 7 份：

```powershell
gcc -std=c99 -O2 -o regress.exe tools\regress.c gait_algo.c -lm
.\regress.exe testdata\expect.txt
.\regress.exe testdata\expect.txt --strict   # 有一条不符就返回 1，可挂 CI
```

输出是一张表（数据集 / 时长 / 台阶 / 已爬层 / 中间平台 / 期望 / PASS-FAIL）。
**现在 `--strict` 会有 6 条 FAIL** —— 这正是 README §11 第 1 条那个已知限制的量化结果，
也是 P0-1（状态机）做完之后必须变绿的那组验收条件。

> **注意"混合运动"这一份的期望值是 2 层，不是 0 层。**
> `ReadMe.doc` 原文写的是"行走 100 步 + **上 2 层楼** + 跑步 100 步 + 跳绳 10 个"，
> 里面藏了真实的两层楼梯。按时间轴拆开看现在的输出：
>
> | 时间段 | 内容 | 算法给出的 FLOOR 事件 |
> |---|---|---|
> | 0 ~ 56 s | 行走 100 步 | 18.6 s、39.3 s（**误报**） |
> | 56 ~ 84 s | **上 2 层楼** | 60.2 s、78.1 s（**正确**） |
> | 84 ~ 118 s | 跑步 100 步 | 91.7 / 100.3 / 109.2 s（**误报**） |
> | 118 ~ 128 s | 跳绳 10 个 | 120.2 s（**误报**） |
>
> 也就是说"上楼梯那一段检测本身是准的"，问题**完全**在于缺少一个"当前是不是在爬楼"的判据。
> 这一条比"平地走 60 s 判 2 层"更能说明问题：既能测误报，也能测漏报。


### 10.5 `/api/ingest` 回放：硬件接上之前的端到端验证

`tools/replay_ingest.py` 用 Python 标准库把整份 txt 按 50 Hz 打成 JSON 批量打到 `/api/ingest`，
**它模拟的正是 STM32 该做的事**：50 Hz 采样、每 100 个样本一个报文、带 `X-Device-Key`。

```powershell
# 先起 server.exe，再另开一个窗口
python tools\replay_ingest.py "D:\数据文件\数据文件\九轴数据文件\上三层楼数据.txt" `
       --device STM32-01 --user collector1
```

跑完最后会打印"已爬 3 层 / 68 级台阶 / floor 事件 3 次"。
**对不上就说明协议或换算有问题，在硬件阶段之前就能发现**，不用等板子焊好。

参数：`--fs`（默认 50）、`--batch`（默认 100）、`--speed`（回放倍速）、`--loop`（重复次数）、
`--dry-run`（只解析不发）。

## 11. 已知限制 / 下一步

1. **没有"是否在爬楼"的判据（最重要）**：现在只要动态加速度超过阈值就记一级台阶，
   楼层 = 累计台阶 ÷ 22。把老师给的其它数据也喂进来会误报：
   下三层楼 → 3 层、日常行走 60 s → 2 层、跑步 → 7 层、跳绳 → 4 层。
   混合运动（ReadMe：行走 100 步 + **上 2 层楼** + 跑步 100 步 + 跳绳 10 个）
   报 8 层，而正确答案是 2 层 —— 其中 60.2 s / 78.1 s 那两次正好落在楼梯段，**是对的**，
   其余 6 次散落在平走、跑步、跳绳段。详见 §10.4 的表。
   也就是说**平地走 / 下楼 / 跑步也会涨楼层**，而且误差会累加、只能靠"重置"清掉。
   题目发挥要求里的"非爬楼期间提示音 2"也需要这个判别能力。
   修复方向：状态机（IDLE → CLIMBING → LANDING）+ 用"到层平台"驱动楼层计数，
   真机陀螺有效后再加"竖直位移积分"做方向判别。**这一步留到硬件阶段做。**
2. **每层 22 级是标定值，不是通用值**：扫描下来 16 级/层会判 4 层、23 级/层会判 2 层。
   建议改成用最近若干层的实测级数做自适应（中位数）。
3. **陀螺数据不可用**：数据集三轴角速度标准差 < 0.1 °/s，现在只用了加速度，方向判别做不了。
   硬件阶段先用 `gyro_check.exe` 验证（见第 8 节），确认有响应后再补方向判别。
4. **`steps15`（每 15 级提示）是别的题目的遗留**：本课题要求是"每级楼梯一声"，
   这个事件和对应的提示音建议删掉，别写进报告当成本题要求。
5. **口令哈希是"快哈希"**：SHA-256 加盐抗暴力破解能力有限，生产应换 PBKDF2/Argon2；
   另外还没有注册/改密接口。
6. **没有用户管理界面**：新增采集对象要直接改 `users` 表。
7. **`raw_samples` 按"行数 + 天数"清理**，不做降采样归档；长期多设备运行建议再加按小时聚合。
8. **`sqlite3.c` 仍在仓库里**（9.4 MB）：为了让 `gcc 一行命令` 就能编，先留着；换 vcpkg/系统库后可以删。
9. 模拟终端的"文件缺失/格式错"只会静默停止，页面上没有明确报错。

## 13. 本轮修复记录（P0-3 ~ P0-6）

只修 bug，**不改算法判据**，所以数据集上的结论（68 级 / 3 层 / 82.0 级·分⁻¹）不变。

| 编号 | 问题 | 改法 | 影响文件 |
|---|---|---|---|
| P0-3 | 终端线程在 `fgets(t->fp)` 时，HTTP 线程可能在 `/api/sim/load`、`/reset` 里 `fclose(t->fp)` → use-after-free（"边跑边切场景"会崩） | 每个 `SimTerminal` 加一把锁；`term_read`/`term_apply_profile`/`sim_reset`/`sim_start`/`sim_set_data_files` 全部持锁；`fclose` 只在持锁时做 | `simulator.c` |
| P0-4 | 模拟端和 `/api/ingest` 都在**不持 `d->mutex`** 时调 `gait_feed()`；`d->gait.cfg.fs = fs` 裸写；快照参数在解锁后才读 `d` | 算法调用 + 状态回填 + 事件处理整段放进设备锁；快照参数在锁内取局部变量；落库放到锁外 | `simulator.c`、`web_server.c` |
| P0-5 | `refractory = 15` 是固定样本数，但 `fs` 允许 1~1000 变 → 端侧 40/100 Hz 时 300 ms 不应期失效 | 新增 `gait_apply_fs()` / `gait_set_fs()`：不应期 300 ms、低通 0.03、滑动平均 100 ms 都按 `fs` 换算；`fs == 50` 时结果与旧版逐位一致；改 `fs` 时窗口长度变化会清空窗口 | `gait_algo.c/h`、`web_server.c`、`db_manager.c` |
| P0-6 | `else if` 链把同一样本上并发的事件（HALF / PAUSE / STEP15）吞掉；`half_flights` 把楼层平台也算进"中间平台"，上 3 层楼页面显示 6 个 | 到层/中间平台保持互斥但其余事件独立处理；新增 `mid_platforms`（真正的半层平台），`half_flights` 明确为"梯段总数"；页面拆成两项显示 | `gait_algo.c/h`、`globals.c`、`global_vars.h`、`simulator.c`、`web_server.c`、`index.html`、`terminal.html`、`tools/*` |

**回归验证（`fs` 无关性，上三层楼数据）**：

| fs | refractory | smooth_len | α | 检出 | 判层 | 中间平台 |
|---|---|---|---|---|---|---|
| 50 Hz（原始） | 15 | 5 | 0.0300 | **68** | **3 层** | 3 |
| 100 Hz（2× 插值） | 30 | 10 | 0.0150 | 72 | **3 层** | 3 |
| 25 Hz（2× 抽取） | 8 | 3 | 0.0600 | 66 | **3 层** | 3 |

> 台阶数在 66~72 之间浮动是重采样本身的平滑/信息损失造成的，**判层数完全一致**，
> 说明"随 fs 换算"这一层是对的。修好之前，40 Hz 跑同一份数据会明显少计（不应期相当于 375 ms）。

`tools/selftest.c` 现在断言 17 项（新增"真正的中间平台 3 个"）。
