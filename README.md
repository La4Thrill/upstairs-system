# SXL2 智能楼梯爬行监测系统（软件设计阶段）

课题：**1、楼梯层数计数（上楼）· 九轴运动传感器**
数据：`上三层楼数据.txt`（2488 样本 @ **50 Hz**，约 49.8 s，上楼 3 层）

## 1. 结论先说：现在的算法对不对？

| 指标 | 旧版本 | 现在 |
|---|---|---|
| 上三层楼数据检出台阶数 | 465（每个样本都是"一步"） | **68 级** |
| 判出楼层 | 24 层（已爬 23 层） | **已爬 3 层 / 当前 4 层** |

| 前端波形量纲 | 原始计数（~9 万） | **g / (°/s)** |
| 平台/到达提示音 | 无 | 6 个中间平台 + 每 15 级 + 到达楼层，音色区分 |

## 2. 系统架构

```
 模拟终端（文件源，50 Hz）                服务端                          前端
┌──────────────────────────┐   ┌───────────────────────────┐   ┌──────────────┐
│ simulator.c              │   │ gait_algo.c（算法，可移植）│   │ index.html   │
│  · 多文件顺序/循环发送    │──►│  原始LSB→g→去重力→台阶     │──►│  · 实时指标  │
│  · 发送行数计数           │   │  →梯段/楼层事件            │   │  · 三条波形  │
│  · 开始/停止/重置         │   │ audio_hint.c（事件→音色）  │   │  · 历史记录  │
│  · 场景 profile/阈值标定  │   │ db_manager.c（SQLite）     │   │  · 角色登录  │
└──────────────────────────┘   │ web_server.c（HTTP+Token） │   └──────────────┘
                               └───────────────────────────┘
```

分层：**采集（simulator）→ 算法（gait_algo，独立静态库）→ 存储（db）→ 展示（web）**。
`gait_algo.c` 不含任何平台相关代码，课程设计阶段可直接编进 STM32F407 工程。

## 3. 算法（为什么能从 465 步变成 68 级台阶）

### 3.1 旧版本为什么错

1. 数据是**有符号 16 位原始计数**（`65338` 实际是 `-198`），旧代码用 `%f` 直接读成 65338，符号和量纲全丢 → `|a|` 常年在 9 万左右。
2. 台阶阈值是常数 `1200`（搭配 `80` 的增量门限），对 9 万的基线恒为真，`cooldown=2` 只能挡住 2 个样本 → **平均每 5.35 个样本就"走一步"**，层数实际等于"样本数 / 107"。
3. 采样间隔写 100 ms，与数据集 50 Hz 不符 → 时间轴、步频错 5 倍。

### 3.2 现在的处理链（`gait_algo.c`）

```
原始 LSB(int16)
  │  ①符号还原 + 量纲换算：/16384 → g（LSM9DS0 ±2g）；/114.29 → °/s（±245dps）
  ▼
加速度模长 |a| (g)
  │  ②去重力：一阶低通 α=0.03（@50Hz ≈0.7s），dyn = |a| − 重力
  ▼
动态加速度 dyn
  │  ③5 点滑动平均降噪
  ▼
  │  ④台阶检测：迟滞 0.18g / 0.09g + 不应期 15 样本(300ms)
  ▼
台阶事件 ──►⑤台阶数 mod 11 → 中间平台(梯段)事件
        ──► 台阶数 mod 22 → 到达楼层事件
        ──► 台阶数 mod 15 → "每跳 15 梯"提示
  │  ⑥动态能量 EMA：RMS<0.14g 持续 0.6s → 平台(真停顿)事件
  ▼
事件 → audio_hint（不同音色）+ /api/status + SQLite
```

### 3.3 参数为什么是这些（标定依据）

用 `上三层楼数据.txt` 标定，`tools/algo_check` 可复现：

| 参数 | 取值 | 依据 |
|---|---|---|
| 采样率 fs | 50 Hz | `九轴数据文件/ReadMe.doc`：所有场景 50 Hz |
| 加速度灵敏度 | 16384 LSB/g | LSM9DS0 ±2g（0.061 mg/LSB） |
| 步态阈值 | 0.18 g（上楼）/ 0.10 g（平地行走） | 上楼动态幅度大；行走起伏小，同一阈值会漏检（实测行走 0.18g→57 级/分，0.10g→91 级/分） |
| 不应期 | 300 ms | 人正常步频上限约 3 步/s |
| 每半层台阶 | 11 级 | 68 级 ÷ 6 个梯段 ≈ 11.3 |
| 每层台阶数 | 22 级 | 68 级 ÷ 3 层 ≈ 22.7，与住宅 18~22 级/层吻合 |
| 楼层上限 | 99 层 | 课题要求 |

**阈值鲁棒性**（上三层楼数据，`stair=1`）：

| 步态阈值 | 0.10 | 0.12 | 0.14 | 0.16 | 0.18 |
|---|---|---|---|---|---|
| 检出台阶 | 82 | 79 | 74 | 71 | 68 |
| 判出楼层 | **3** | **3** | **3** | **3** | **3** |

阈值在 0.10~0.18 g 之间变化时结论稳定为 3 层，说明层数判定不依赖阈值精调。

### 3.4 场景 profile

| profile | 数据 | 循环 | 判层 | 说明 |
|---|---|---|---|---|
| `upstairs3` | data1 | 默认单次 | 是 | 上楼演示；跑完 2488 样本自动停在 **3 层** |
| `dailywalk` | data2 | 默认循环 | 否 | 对照：只计步（≈92 级/分），不累加楼层，验证"干扰不误判" |
| `mixed` | data1+data2 | 默认循环 | 否 | 混合场景：验证多文件顺序发送 |

"循环发送"可在页面勾选（`loop` 参数），`upstairs3` 默认单次，便于验收时结果确定。

## 4. API（相对旧版本的变化）

| 接口 | 变化 |
|---|---|
| `POST /api/login` | 返回 `token`（后续请求带 `X-Auth-Token`） |
| `GET /api/status` | 新增 `speed`（级/分）、`half_flights`、`on_platform`、`last_event`、`last_hint`、`last_event_time`、`fs`、`steps_per_floor`、`stair_mode`；`dyn_wave`（分析后波形）；波形改为物理量 |
| `POST /api/sim/load` | 参数 `{"profile":"upstairs3","loop":false}`，返回 `stair_mode` / `loop` |
| `GET /api/history` | 数据来源改为"每 5 s 快照 + 到达楼层事件"，不再每一步写一行 |
| `POST /start` `/stop` `/reset` | 需 admin/monitor 角色 |
| 页面 | 新增步频、中间平台数、平台状态、最近事件/提示音、动态加速度波形（含阈值线）、循环发送开关 |

默认账号：`admin/admin123`、`monitor1/monitor123`、`collector1/collector123`、`collector2/collector123`。

## 5. 构建与运行

### 5.1 CMake（推荐，VS / Ninja / MinGW 均可）

```powershell
cmake -S . -B build
cmake --build build --config Release -j 4
.\build\Release\server.exe
```

### 5.2 直接用 gcc（MinGW，最快验证）

```powershell
gcc -std=c99 -O2 -o server.exe server.c globals.c web_server.c simulator.c gait_algo.c `
    db_manager.c audio_hint.c cjson.c sqlite3.c -lws2_32 -lwinmm -lm
.\server.exe
```

浏览器打开 <http://127.0.0.1:8080/>，登录 → 选"上三层楼数据" → 加载文件 → 开始。


## 7. 已知限制 / 下一步（硬件阶段）

1. **多终端仍是单通道**：模拟器只写 `g_users[0]`，`users/devices/raw_samples` 三张表建了但未写入，历史不区分用户。→ 下一步把文件源抽成 `data_source` 接口，新增 `/api/ingest` 供 STM32 上报，按 `device_id` 分通道。
2. **数据集里陀螺三轴基本是常量**（std < 0.1 °/s，见下表），实际只有加速度可用，所以本算法只用了加速度：
   ```
   gyro_x mean -5.77 dps std 0.07 | gyro_y 1.49 std 0.06 | gyro_z -8.35 std 0.05
   ```
   这意味着**上下楼方向判别没法靠陀螺**。硬件阶段必须确认 LSM9DS0 陀螺是否真的出数（量程/使能/接线），再补方向判别。
3. 行走场景与上楼场景的阈值不同，当前按 profile 标定；真实设备上应做自适应阈值（按最近 N 步峰值中位数）。
4. 密码仍是明文入库、`auth_accounts` 每次启动重建；`raw_samples` 未使用；`build/`、`*.db`、`server.pid` 仍在仓库里。→ 建议在提交前清理（见评审记录的 P1 项）。
5. 提示音目前在服务端 PC 上响（`PlaySound`）；硬件阶段改成端侧蜂鸣器，事件编码不变。
